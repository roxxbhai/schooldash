# Backend architecture (Phase 7)

The backend follows the root `AGENTS.md`. All application code lives under
`src/`. There is no separate service or repository layer: each route handler
holds its own request schema and simple queries, and logic shared between routes
lives in `src/functions/<module>/index.ts`.

## Folders

| Folder | Holds | Rules |
| ------ | ----- | ----- |
| `src/app/api/<resource>/…/route.ts` | Route handlers | Parse and validate the request, run the guard, perform single-use queries, respond. |
| `src/functions/<module>/index.ts` | Server operations shared by routes: lookups, authorization, business rules | `import 'server-only'`. Every exported function has its own `try`/`catch` and returns the standard result (below). |
| `src/helpers/<module>/index.ts` | Reusable utilities: errors, responses, request validation, query wrappers, CSRF, logging, Supabase client factories, pure domain checks | Throwing or pure. No standard-result wrapping. Server-only, except `supabase-browser` and `supabase-proxy`. |
| `src/constants/<module>/index.ts` | Column lists, constraint-to-message maps, shared request-field schemas, limits | Stable values only. |
| `src/types/<module>/index.ts` | Row types (from the generated schema), API and result types | `src/types/database` is generated by `npm run db:types`; never edit it by hand. |
| `src/configs/index.ts` | Environment validation (`getSupabaseEnv`, `getSupabaseAdminEnv`) | Server-only and lazy, so the app builds without configuration. |
| `src/proxy.ts` | Next.js 16 proxy: refreshes the Supabase session cookie | It authorizes nothing. |

Modules (`<module>` names): `academic-years`, `subjects`, `classes`,
`teachers`, `students`, `enrollments`, `teacher-assignments`,
`student-attendance`, `teacher-attendance`, `exams`, `exam-subjects`,
`results`, `report-cards`, `timetable`, `notices`, plus the shared `session`,
`authorization`, `provisioning` and `account-status`.

## The function result contract

Every function in `src/functions` returns:

```ts
{ success: true, message: 'Operation successful', data: T }
{ success: false, message: '<client-safe message>', data: { status, code, details? } }
```

The failure carries the HTTP status, error code and field-level details. This
keeps the API's `{ data, error }` responses identical to before the refactor.

- **Inside a function:** its `try`/`catch` turns anything thrown into a failure
  with `functionFailure()`. Unexpected errors are logged there, once, as
  metadata only, and reach clients only as a generic 500, or 503 when Supabase
  is unreachable.
- **In a route (or another function):** `unwrapResult(result)` returns `data`,
  or rethrows the failure as the same `ApiError`. The route wrapper `apiRoute`
  is the single place that turns errors into responses.
- **For a record the request body references:**
  `unwrapReference(result, field, message)` turns a 404 into a 422 on that
  field.

**Never use a result as if it were its data.** A result object is always truthy,
so `if (!(await teachesClass(…)))` would silently skip an authorization check.
Unwrap it or check `.success`. The Phase 7 audit checked every call site for
this.

## API contract (unchanged)

- Success: `{ data, error: null }`. Collections:
  `{ data: { items, pagination: { page, limit, total, totalPages } }, error: null }`.
- Failure: `{ data: null, error: { code, message, details? } }`, with the status
  codes documented in `docs/school-api.md`.
- Database errors are mapped by constraint name in `src/helpers/db-error`.
  Raw SQL, hints and details never leave the server.

## Conventions

- Files and folders are kebab-case (`<module>/index.ts`); variables and
  functions are camelCase; booleans start with `is`.
- Single quotes (enforced by ESLint for backend, test and script files).
  Comments are uppercase, except code identifiers inside them.
- Named functions use `function` declarations. Short inline callbacks
  (`.map((row) => row.id)`, Zod refinements) stay as arrows. That is the one
  deliberate exception to `AGENTS.md`'s arrow-function rule, chosen for
  readability.
- Supabase result types come from the generated schema. Where a select string
  has embeds the type parser can't follow, `.overrideTypes<T, { merge: false }>()`
  states the type explicitly. There are no `as never` casts.

## Tests

| Suite | Command | Talks to Supabase? |
| ----- | ------- | ------------------ |
| Unit tests | `npm test` | **No.** Route handlers run in-process against `tests/helpers/fake-db.ts`, a recording stand-in for the Supabase query builder used only in tests. Guards are stubbed by `tests/helpers/route-harness.ts` with the same role rules. Session and guard logic is tested against `tests/helpers/fake-supabase.ts`. |
| Integration tests | `npm run test:integration` | **Yes, the real project.** Real sessions, RLS, grants, triggers and constraints. See `docs/school-api.md` § Testing. |

`tests/server-only.test.ts` enforces:
- every server module imports `server-only`;
- only config and the admin client read the secret key;
- only provisioning and account status use the admin client;
- only the two admin-guarded people routes import provisioning, and both call
  `requireAdmin` before it.
